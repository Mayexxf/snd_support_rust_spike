# Стенд замеров, фаза 0

Отвечает на два из трёх вопросов, которые план ставит **до** всякой архитектуры:
успевает ли целевая машина снимать собственный экран и какая доля этого экрана
на самом деле меняется. Третий вопрос — сквозная задержка через реле — требует
транспорта и в этот стенд не входит.

Код одноразовый. При удаче `spike-capture` переезжает в `snd-capture`, остальное
выбрасывается вместе с закрытием фазы.

## Порядок, ради которого это сделано

1. **Сначала на виртуальной машине** — убедиться, что стенд собирается и работает.
2. **Потом одна ходка на целевой Celeron N3150** — за настоящими цифрами.

Отчёт начинается с описания машины и сам говорит, переносятся его цифры на целевую
или нет. Виртуальная машина, чужая архитектура и наличие AVX помечаются отдельно:
у Braswell AVX нет, и процессор с ним даст программному кодеру фору, которой на
целевой машине не будет.

## Сборка

```bash
cargo build --release
```

На Windows этого достаточно. Никаких внешних C-зависимостей на этом этапе нет —
`libvpx` появится вторым заходом, вместе с кодированием.

Домен собирается и тестируется на любой ОС, Windows нужен только для настоящего
захвата:

```bash
cargo test
```

## Кодирование: libvpx

Выключено по умолчанию. Захват меряется без него, и ставить vcpkg ради этого
незачем.

Ставить **на сборочную машину, не на целевую**: на целевой Celeron должен
оказаться готовый `.exe`, а не сборочная площадка. Бинарь самодостаточен —
`+crt-static` из `.cargo/config.toml` убирает зависимость от Visual C++
Redistributable.

### Три шага

```powershell
git clone https://github.com/microsoft/vcpkg
.\vcpkg\bootstrap-vcpkg.bat
.\vcpkg\vcpkg install libvpx:x64-windows-static
```

**Триплет именно `x64-windows-static`, а не `-static-md`.** Мы линкуем статический
C-рантайм (`+crt-static`), и `-static-md` — сборка под динамический — даст при
линковке `LNK2038: mismatch detected for RuntimeLibrary`. Ошибка выглядит
непонятно, а причина ровно эта.

Сборка libvpx из исходников занимает от десяти минут до получаса: vcpkg сам
подтягивает nasm, perl и msys.

```powershell
winget install LLVM.LLVM
```

LLVM нужен bindgen'у, и обойтись без него не выйдет ни одним из путей: готовые
биндинги в `env-libvpx-sys` заканчиваются на 1.13.0, vcpkg даёт 1.16.0, а
ShiftMediaProject — 1.15.1. Биндинги генерируются по настоящим заголовкам. Это надёжнее, а не хуже: расхождение ABI не выдало бы
ошибку сборки, оно испортило бы память и напечатало правдоподобные числа.

### Если vcpkg не может скачать msys2

vcpkg собирает libvpx из исходников и тянет для этого msys2, nasm и perl. В
закрытой сети это тупик, и распознаётся он по двум разным симптомам.

`curl error 6 (Could not resolve hostname)` — отказ DNS. Бывает разовым: vcpkg
считает такую ошибку невосстановимой и не повторяет попытку, хотя имя
разрешилось бы секундой позже. Проверьте `nslookup repo.msys2.org` и запустите
установку заново.

**Если имя разрешается, а загрузка висит** — дело не в DNS, а в исходящем
соединении: корпоративный прокси или фильтрация. Своего прокси у vcpkg нет, и
ждать бесполезно. Переходите на готовую сборку.

Готовая libvpx —
[ShiftMediaProject/libvpx](https://github.com/ShiftMediaProject/libvpx/releases),
файл `libvpx_v1.15.1_msvc17.zip` (msvc17 — это Visual Studio 2022). Ни msys2, ни
nasm, ни perl тогда не нужны: распаковать и указать пути. Заголовки лежат в
`include/vpx/`, статическая библиотека — в `lib/x64/libvpx.lib`, именно под тем
именем, которое ищет `env-libvpx-sys`. Соседний `lib/x64/vpx.lib` — библиотека
импорта для DLL, она не нужна.

**У этого пути есть цена, и она не косметическая.** Готовая сборка собрана с
динамическим C-рантаймом: в `libvpx.lib` 235 директив `DEFAULTLIB:"MSVCRT"`. Наш
`+crt-static` — статический рантайм, и компоновщик ответит `LNK2038: mismatch
detected for RuntimeLibrary`.

Для этого случая в репозитории лежит `.cargo/dynamic-crt.toml`. Он подставляется
ключом `--config` и переопределяет флаги только для Windows-цели:

```powershell
cargo run --release --features vpx --config .cargo\dynamic-crt.toml -- --encode vp9 --seconds 30
```

Отдельным файлом, а не правкой `.cargo/config.toml`, потому что флаги приходится
перечислять целиком, и потерять среди них `target-cpu=x86-64` нельзя: без него
бинарь умирает на Celeron с `0xc000001d` до первой записи в лог. В правленом
конфиге легко забыть вернуть флаг обратно; через `RUSTFLAGS` ещё хуже —
переменная **заменяет** флаги конфига целиком, и `target-cpu` исчезнет молча.
Здесь он выписан в файле, где его отсутствие видно глазом.

Последствие: бинарю понадобится Visual C++ Redistributable на целевой машине. На
заброшенной старой машине его может не быть, и тогда приложение не запустится
вовсе. Для замерочного стенда это терпимо — поставьте redist заодно, — но для
продукта правильным остаётся путь через vcpkg с триплетом `x64-windows-static`.

### Переменные окружения

Через vcpkg:

```powershell
$sdk = "C:\vcpkg\installed\x64-windows-static"
$env:VPX_LIB_DIR = "$sdk\lib"; $env:VPX_INCLUDE_DIR = "$sdk\include"
$env:VPX_VERSION = "1.16.0"; $env:VPX_STATIC = "1"
$env:LIBCLANG_PATH = "C:\Program Files\LLVM\bin"
```

Через готовую сборку — свой каталог распаковки и версия из имени архива:

```powershell
$sdk = "C:\libvpx"
$env:VPX_LIB_DIR = "$sdk\lib\x64"; $env:VPX_INCLUDE_DIR = "$sdk\include"
$env:VPX_VERSION = "1.15.1"; $env:VPX_STATIC = "1"
$env:LIBCLANG_PATH = "C:\Program Files\LLVM\bin"
```

`VPX_VERSION` обязана совпадать с тем, что стоит: она уходит в проверку ABI при
инициализации кодера. У 1.13 эта версия равна 30, у 1.15 — 37, и несовпадение
libvpx поймает сама.

### Если сборка падает на «no field `g_w` on type `vpx_codec_enc_cfg`»

Пятнадцать ошибок про неизвестные поля и подсказка `available field is:
_address` означают одно: bindgen не нашёл заголовки libvpx. Он при этом **не
падает** — выдаёт неполные типы и позволяет сборке дойти до места, где они
используются. Причина всегда в путях, а не в коде.

Сборочный скрипт `spike-encode` проверяет настройку заранее и печатает, чего
именно не хватает. Проверить руками:

```powershell
Get-ChildItem "$env:VPX_INCLUDE_DIR\vpx\vpx_encoder.h"
```

`VPX_INCLUDE_DIR` указывает на каталог, **внутри** которого лежит подкаталог
`vpx\` — то есть `C:\libvpx\include`, а не `C:\libvpx\include\vpx`.
Проверьте заодно, не создал ли распаковщик лишний уровень вложенности вида
`C:\libvpx\libvpx_v1.15.1_msvc17\include`.

Если пути верны, а типы всё равно пустые — clang не нашёл **системные заголовки
Windows**: `vpx_integer.h` включает `<stdint.h>`, и libclang вне окружения
Visual Studio до него не дотягивается. Собирайте из **Developer PowerShell for
VS 2022** — переменные окружения libvpx придётся задать в ней заново.

Увидеть, на что жалуется clang, можно так — вывод сборочных скриптов иначе
скрыт:

```powershell
cargo build --release --features vpx --config .cargo\dynamic-crt.toml -vv 2>&1 | Select-String -Pattern "clang|fatal|error" | Select-Object -First 30
```

### Сборка и прогон

```powershell
cargo run --release --features vpx -- --encode vp9 --seconds 30
```

Без `--features vpx` запрос кодирования — ошибка, а не тихий откат: прогон,
молча пропустивший кодирование, напечатал бы приятный бюджет и не ответил бы ни
на что.

## Прогоны

```bash
# Проверка стенда без настоящего экрана — идёт где угодно, включая macOS
cargo run --release -- --source synthetic --motion scroll --seconds 10

# Статичный рабочий стол. Не трогайте мышь весь прогон
cargo run --release -- --source dda --seconds 60

# Прокрутка документа. Крутите колесо ровно и непрерывно
cargo run --release -- --source dda --seconds 60

# Если DDA не открылась — что на виртуалке обычное дело
cargo run --release -- --source gdi --seconds 60
```

### Сравнение путей копирования

**Один** прогон. Оба пути копируют один и тот же кадр, порядок чередуется, так
что ни одному не достаётся всё время холодный кеш.

```bash
cargo run --release -- --readback compare --seconds 30
```

Двумя отдельными прогонами это не меряется, и первая попытка это показала:
495 опросов против 972, разное содержимое, совпадение доли изменившейся площади
по удаче. Никто не крутит документ дважды одинаково.

Частота кадров в этом режиме занижена — на каждый кадр приходится две копии.
Значение имеют только строки сравнения.

Ожидание — выигрыш примерно обратно пропорционален доле изменившейся площади.
Если он заметно больше, дело не в экономии байтов, а в том, что путь копирования
целой текстуры на этой машине уходит куда-то не туда; если меньше — много мелких
переносов проигрывают одному большому. Обе новости полезны, и обе бывают.

## Какая сборка это напечатала

Шапка отчёта содержит строку `сборка стенда` с коммитом и пометкой `+правки`,
если рабочее дерево от него отличается. Стенд ездит между машинами, а его вывод
и есть результат работы — так что вопрос «какая сборка дала эту таблицу»
задаётся про каждую. Однажды он уже стоил лишнего прогона: правка выглядела
неработающей, а был запущен старый бинарь.

## Как читать отчёт

**`экран не менялся`** — доля опросов, на которых рабочий стол был неподвижен.
На этой доле держится весь бюджет кодирования: неподвижный кадр не кодируется
вовсе. Если на статичном столе она не близка к 100%, что-то на машине рисует
постоянно, и это надо найти до всех остальных выводов.

**`менялось за кадр`** — доля площади в изменившихся прямоугольниках. Пересечения
считаются дважды намеренно: дедупликация польстила бы бэкенду, а кодер платит за
те прямоугольники, которые ему отдали.

**`ожидание кадра` — не расход.** При цели 30 к/с источник обязан большую часть
времени ждать. Сложенное с работой, ожидание превратило бы неподвижный стол в
перегруженную машину — вывод, обратный истине.

**`ИТОГО на кадр`** и **`Бюджет кадра`** — то, ради чего всё. Это работа захвата
плюс копирование в память плюс кодирование, сложенные **на каждом кадре
отдельно**, а не собранные из трёх перцентилей: p95 суммы не равен сумме p95.
Вердикт выносится по p95, а не по медиане, потому что сеанс оценивают по худшим
моментам. Пороги намеренно строгие: клиентская машина должна ещё тянуть мастер и
то, чем пользователь вообще-то занят.

**`Вердикта не будет`** — кадров с содержимым меньше тридцати. Это не сбой:
на неподвижном столе так и должно быть. Просто при малом числе выборок `p95` —
это буквально худший кадр, и вердикт описывал бы один неудачный кадр, а не
машину. Стоимость кадра меряется прогоном **с движением**; неподвижный прогон
отвечает на другой вопрос — как часто экран вообще меняется.

**`конвертация в YUV`** — отдельная стадия, а не часть кодирования. libvpx
принимает планарный YUV, а захват отдаёт только BGRA; у RustDesk та же стадия
(`convert_to_yuv`) и та же обязанность за неё платить. Отдельно она потому, что
оптимизируется независимо — идёт по изменившимся областям, а в продукте пойдёт
через SIMD. Спрятанная внутрь кодера, медленная конвертация выглядела бы как
медленный кодек и увела бы работу не туда.

**`копировалось за кадр`** — сколько площади реально уехало из памяти GPU.
Читать вместе с `менялось за кадр`: если частичное копирование работает, числа
близки; если оно упёрлось и копирует всё подряд, первое стоит на 100%, а второе
нет. Расхождение и есть цена, которую платят зря.

**`потеря доступа к экрану`** — сколько раз DDA отдала `ACCESS_LOST`. Это не сбой,
а норма живой машины: экран блокируется, появляется окно UAC, меняется
разрешение. Считается именно потому, что частота этих событий и есть один из
вопросов фазы 0.

## Две вещи, которые стенд сообщает о себе

**Разрешение таймера.** По умолчанию Windows квантует ожидания шагом 15,6 мс,
поэтому таймаут в 33 мс превращается в 46,9 мс, и опрос идёт не на 30 Гц, а на
21. Это замерено на первом же прогоне, а не предположено. Стенд поднимает
разрешение таймера на время работы и возвращает обратно при выходе; строка в
шапке говорит, удалось ли.

**Программный адаптер.** Если DXGI отдаёт «Microsoft Basic Render Driver» или
другой WARP, настоящего GPU нет — внутри виртуальной машины это обычное дело.
Захват при этом работает и цифры выглядят правдоподобно, но строка
«копирование в память» меряет память, а не шину GPU. Стенд предупреждает об
этом отдельной строкой, потому что правдоподобная неверная цифра хуже
отсутствующей.

## Чего стенд не делает

- **Не измеряет сеть.** Реле, дырокол и сквозная задержка — отдельная работа.
- **Не заменяет приёмку с мобильного хотспота.** Она остаётся обязательной.
